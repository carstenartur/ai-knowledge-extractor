# Public distribution

Public distribution is prepared, but **no public availability is established by merging this
tooling or passing its rehearsal**. The existing 0.2.0 release remains a GitHub Packages / GitHub
Releases release. Issue [#100](https://github.com/carstenartur/ai-knowledge-extractor/issues/100)
stays open until account prerequisites and a real anonymous consumer run are complete.

## Coordinates and dependency graph

| Consumer | Public coordinate / channel |
| --- | --- |
| Java Core API | `org.aiknowledge:ai-knowledge-core:X.Y.Z`, Maven Central |
| Maven plugin | `org.aiknowledge:ai-knowledge-maven-plugin:X.Y.Z`, Maven Central |
| Gradle plugins DSL | `org.aiknowledge.extractor` version `X.Y.Z`, Gradle Plugin Portal |
| Gradle marker | `org.aiknowledge.extractor:org.aiknowledge.extractor.gradle.plugin:X.Y.Z` |
| Marker implementation | `org.aiknowledge:gradle-plugin:X.Y.Z`, depends on released Core |
| Existing explicit Gradle implementation coordinate | `org.aiknowledge:ai-knowledge-gradle-plugin:X.Y.Z` |

The two Gradle implementation coordinates already exist in the build. Both are retained; the
marker graph is tested explicitly. Every binary publication includes sources and Javadoc JARs.
Every POM, JAR and Gradle module metadata file is signed in public mode. POMs include license,
maintainer and SCM metadata; Central checksums are generated by the publishing plugin.

## One-time maintainer setup

These steps can be completed through the services' web interfaces and a browser-accessible
development environment, without installing publishing tools on a local workstation.

1. Create a [Central Portal account and verify the namespace](https://central.sonatype.org/register/namespace/).
   `org.aiknowledge` requires ownership accepted by Central. A GitHub repository with this project
   name does not establish ownership. If the namespace cannot be verified, make a separately
   reviewed coordinate and plugin-ID decision before publishing; do not silently substitute a group.
2. Generate a [Central Portal user token](https://central.sonatype.org/publish/generate-portal-token/).
   The token username/password differ from the interactive account login.
3. Provision a signing key and distribute its public key according to
   [Central's signing requirements](https://central.sonatype.org/publish/requirements/gpg/).
   Browser-based Codespaces can run GPG if needed. Export private material directly to a temporary
   file and enter it through GitHub's secret UI; keep it out of logs, commits and workflow artifacts.
4. Create the [Gradle Plugin Portal account and API keys](https://docs.gradle.org/current/userguide/publishing_gradle_plugins.html#account_setup).
   Confirm the account can publish `org.aiknowledge.extractor`. Initial Portal review can delay
   availability after a successful upload.
5. Create the GitHub Actions environment **public-distribution**. Restrict deployment branches to
   `main` and configure a required maintainer review. Give publishing tokens only their required
   namespace/plugin rights; the workflow's GitHub token has read access only.
6. Add these environment secrets and variable through repository **Settings → Environments**:

| Name | Type | Value |
| --- | --- | --- |
| `MAVEN_CENTRAL_USERNAME` | Secret | Central user-token username |
| `MAVEN_CENTRAL_PASSWORD` | Secret | Central user-token password |
| `MAVEN_SIGNING_KEY` | Secret | ASCII-armored private signing key |
| `MAVEN_SIGNING_PASSWORD` | Secret | Key passphrase, empty only for an unprotected key |
| `GRADLE_PUBLISH_KEY` | Secret | Portal API key |
| `GRADLE_PUBLISH_SECRET` | Secret | Portal API secret |
| `CENTRAL_NAMESPACE_VERIFIED` | Variable | Exactly `org.aiknowledge`, after actual verification |

The variable is an explicit maintainer record, not independent proof of namespace ownership;
Central still enforces ownership. No secret is needed for CI or `validate` / `verify-public` runs.

## Rehearsal in every CI run

`.github/scripts/verify-public-distribution.sh`:

1. selects the candidate's stable version and creates a temporary CI-only signing key;
2. publishes all publications into a disposable file repository and validates the Gradle plugin;
3. checks the actual marker dependency graph, internal versions, POM completeness, binary/source/
   Javadoc JARs, signatures and checksums;
4. creates consumer projects outside the checkout with empty Gradle/Maven caches and settings;
5. runs the Gradle marker, Maven plugin and direct Core API against the staged binary artifacts;
6. verifies retained schema-v2 outputs and an actual Java/TypeScript boundary link.

The private test key is deleted. `public-distribution-rehearsal` retains public diagnostics and a
SHA-256 manifest. Its summary always says `publicAvailabilityVerified: false`. This proves local
publication correctness, not acceptance by either service.

The Portal's `publishPlugins --validate-only` still requires publishing keys in plugin-publish
2.1.1. That check runs with real credentials immediately before the protected Portal upload;
credential-free CI validates the local plugin and its actual publication metadata instead.

## Publish from GitHub Actions

First create a normal supported release using the [release process](release.md). Use a **future
release whose tag contains this tooling**; historical tags are not rewritten. Open Actions →
**Public distribution** → **Run workflow**, select `main`, enter its exact `X.Y.Z`, and proceed:

1. `validate`: qualify the release and run the complete signed rehearsal.
2. `publish-central`: after the protected environment review, publish the signed artifacts and
   wait for Central's `PUBLISHED` state.
3. `publish-portal`: verify that Core and the marker implementation resolve on Central, then upload
   the Gradle plugin. The subsequent independent job attempts anonymous consumption of both channels.
4. `verify-public`: rerun only qualification and anonymous consumption after repository propagation
   or initial Portal approval. This mode cannot upload anything.

Qualification applies the **current** supported-line policy, rejects unsupported/schema-v1 lines,
requires a stable non-draft GitHub release with `SHA256SUMS`, checks tag/release-branch identity,
and proves the release commit changes only version metadata after an exact CI-qualified source
parent on the supported branch. All following jobs check out that resolved commit SHA. CI rules
exercise rejection of post-qualification code changes, stale success, draft releases and invalid
versions. A maintenance line needs an explicit compatible backport before it can use this tooling.

Only a successful **anonymous-public-consumers** report with `publicAvailabilityVerified: true`
establishes both channels' availability. It uses the Portal exclusively for our Gradle marker and
Central for implementation/Core resolution. Maven uses only its default Central repository. Both
run with empty caches, empty Maven settings and an environment stripped of credentials, with no
composite build, `mavenLocal()` or GitHub Packages fallback. Preserve the workflow URL, exact SHA,
candidate record and reports when updating the release notes and closing #100. The recorded SHA
and checksums identify build inputs/outputs; they are not a cryptographic build attestation.

## Partial failures and recovery

- If validation/signing fails, fix the source and prepare a new qualified candidate.
- If a Central upload times out, inspect its deployment state before retrying. Do not blindly
  upload a version that may already be published. After Central succeeds, select only
  `publish-portal` for the missing channel.
- If the Portal is awaiting approval, rerun `verify-public` after approval; avoid duplicate uploads.
- If anonymous resolution fails because of propagation, retain the failing report and rerun
  `verify-public`. Never replace the check with a cached or authenticated consumer.
- Public versions are immutable. Correct a bad public release with a new patch; do not retag,
  overwrite binaries or imply that deleting a GitHub release removes Maven Central artifacts.
- State partial availability explicitly. Update documentation to advertise both public channels
  only after both consumer checks succeed.

Implementation follows the publisher's [base plugin](https://vanniktech.github.io/gradle-maven-publish-plugin/base/)
and [Central publishing](https://vanniktech.github.io/gradle-maven-publish-plugin/central/) documentation,
and Gradle's [Plugin Portal publication guide](https://docs.gradle.org/current/userguide/publishing_gradle_plugins.html).
